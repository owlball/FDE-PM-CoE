Getting set up in SAP

Before your first engagement, you need a working SAP environment. None of this is automatic — plan a few days for setup.

Your VDI

Your primary workstation is a cloud-based Virtual Desktop Infrastructure (VDI) running Windows 11, hosted on Azure.

Creating it:

  • Must be done from the shared SAP VDI first — you cannot order it from your own machine
  • Go to url.sap/desktopcloud and click + to create a new desktop
  • Choose Windows 11 Cloud PC — Azure East US 2
  • Recommended spec: Standard_E8s_v5 (8 vCPU, 64 GiB RAM, Memory Optimized)
  • Set an auto-shutdown time to avoid unnecessary chargeback
  • Once provisioned, your personal VDI appears in the Windows App under US - East US 2 - Virginia as a named entry (e.g. AZREU2055013). The shared desktop under US - East US 2 - Virginia - Shared Desktops remains — that's a different machine. Connect to your personal one.
  • Provisioning takes a while after creation — log in within 24 hours of receiving the "ready" email or the machine may be stopped

Where to save your work:

  • Always store client work in OneDrive — VDIs can be lost and your files go with them. Use the standard folder structure for all engagement work — see FDE Tools for the layout.
  • Local-only work (practice, one-offs) should live on the VDI itself

VDI lifecycle — emails to watch for:

  • Expiry notice — VDIs expire roughly every 5 months. Go to the DesktopCloud app to extend before the deadline; if you do nothing it gets stopped automatically
  • Disk expansion notice — if your VDI runs low on disk, IT schedules a forced shutdown and expansion. Save all open work and shut down yourself before the deadline — if IT does it, unsaved work is lost

Claude Code

Install Claude Code and the Hyperspace AI Desktop App on your VDI. Follow the SAP Media Share video guide: Watch installation video →

A few things that catch people out:

  • You cannot paste images into the CLI directly — paste the file path instead, or drag a file from Explorer to copy its path
  • Opening multiple CLI tabs gives you multiple independent Claude instances — useful for parallel work
  • The VS Code extension lets you paste images directly but only supports one conversation at a time
  • Run interactive shell commands from the Claude CLI by prefixing with ! so the output lands in the conversation

Claude Code runs only in the terminal inside your VDI. There is no claude.ai web app or desktop app access on SAP machines — the terminal is the only entry point.

Spending limits: Claude Code has a $100/month default limit, extendable once to $200. The daily default is $10, increasable in $10 increments. Plan around the $200/month ceiling — tier upgrade requests have not been answered. To check your current spend and remaining budget, open the Hyperspace AI app — it shows daily and monthly limits, session cost, and token counts.

Admin processes

These each have their own process — do not assume one applies to the other:

  • Calendars — you have both an SAP and an ACN calendar; keep both updated to avoid conflicts
  • PTO — coordinate with your SAP manager directly and give plenty of notice
  • Fieldglass — draft and submission each follow their own process; reach out to HR support for SAP FDE if you have not done it before
  • Holiday schedules — SAP and ACN holidays differ. When one company observes a holiday the other does not, documentation is required — reach out to ACN HR for SAP FDE for the process.
  • All interactions with SAP colleagues and systems — use your SAP account, not your ACN account

What an FDE PM does

FDE PM work splits into two phases: Discovery (six weeks, use case validation through Go/No-Go) and Execution (90 working days, building and delivering the solution). You will typically be assigned to one phase at a time — a PM who ran Discovery hands off to an Execution PM at the Go/No-Go decision. The rest of this section covers the Discovery role. For Execution, see Starting an Execution engagement below.

The Discovery role

As an FDE PM you are the engagement. You are the client's primary SAP contact, you own every deliverable, and you bring both the product management discipline and the SAP domain knowledge. The rest of the team — Discovery Lead, Engineer, Value Advisor — supports you on specific activities. You are the only person who is fully committed for all six weeks.

Your four core responsibilities:

  • Shape the use case — identify the highest-value candidate from the SAP AI portfolio and the customer's own backlog. Kill everything else. Confirm the shortlist in writing.
  • Own the spec — produce a Draft Product Spec that an engineer can implement without asking follow-up questions. You co-author the backend chapters with the Engineer.
  • Own the client relationship — you run every working session, chase every open item, and are accountable for the Go/No-Go outcome.
  • Bring SAP product depth — you understand which APIs exist, which processes SAP already covers, and where the portfolio gaps are. The Engineer understands the systems — you understand the products.

Read this first: The Discovery Guide & Templates site is the authoritative reference for the full process. This guide tells you how to navigate it — not replace it.

Discovery deliverables

The handoff package you deliver at the end of Discovery consists of six artifacts:

Draft Product Spec

The full functional and technical specification the Execute team builds against. You own it; you co-author the agent logic and data chapters with the Engineer. Every TBD in the agent logic section is a Sprint 0 blocker. Use the Spec Builder to generate a formatted Word document from the Markdown file.

Logic diagram

A workflow diagram of every action the TO-BE solution can take — the full decision tree of steps, branches, and possible paths from start to finish.

User Journey

A map of the user's experience with the solution end-to-end — the stages they move through, what they're doing and thinking at each point, and where friction or opportunity exists.

UX state diagram

Documents every UI state and what happens at each one — which screens appear, what each button does, and which paths open depending on the logic at that point.

UI SPA

A single-page app showing the agent UI. Built in W4–W5 and shown at the executive sign-off session.

Prototype

A thin-slice backend run against real customer records to validate the TO-BE design before committing to Execute.

Connecting to the SAP AI roadmap

Every use case candidate must be checked against the SAP AI portfolio before it is confirmed. Use Neo and the FDE Engagement Tracker. Mark each candidate as one of:

  • Not covered yet — clear path for FDE
  • Overlap — call the LOB PM before committing; may still be viable as a bridge or extension
  • Already covered — do not proceed; redirect the customer to the existing product

A conflict discovered at the Go/No-Go meeting derails the decision. Surface it in W1.

The Go/No-Go decision

The Scorecard has four criteria, each scored HIGH/MED/LOW: Customer Value, Feasibility, Productizability, and SAP Value.

  • GO — all four HIGH
  • CONDITIONAL GO — no LOW, not all HIGH — name the gap and a hard deadline
  • NO-GO — any LOW

A score without a named source does not count. Every evidence cell must cite a specific artefact. You prepare the presentation and present to the Go/No-Go panel. The backing data comes from the templates filled throughout Discovery.

Handing off to Execute

A Go decision does not start Execute automatically. You own the scope statement in W6 — four dimensions: organisational reach, functional surface, data and systems, and outcomes and guardrails. Anything not in the scope statement at that point is out of scope for Execute.

What an Execution PM does

The Execution PM owns the 90-working-day window from Go/No-Go to go-live. Where the Discovery PM validates and specifies, the Execution PM delivers.

Three core responsibilities:

  • Accept and own the scope — formally accept or return the handoff package. Everything in scope at handoff is yours to deliver. Anything not in the scope statement is out of scope.
  • Run the engagement — set up the operating model from scratch in Week 1, run the sprint cadence, manage the client relationship, and keep the delivery team unblocked. You are the primary client contact for the duration.
  • Manage scope and risk — escalate scope drift and overrun risk early. The 90-day window is fixed; trade-offs inside it are yours to make.

Note: The Execution PM role is called Project Manager in the Book of FDE and in FDE on MXP.

This role may involve travel to the client's site for on-site working sessions.

Execution timeline

The Execution phase runs ~12–13 weeks / 90 working days. It ends when the first customers go live under Early Adopter Care (RTC EAC).

PeriodWhat happens
Week 1Operating model setup — SharePoint, Outlook distro, client access, communication channels, Week 1 artifacts
SprintsTwo-week sprints with standups, weekly client sync, sprint demos, and retrospectives
Every 2 sprintsOn-site 2–3 day working session: demo, data validation, backlog reprioritization, next-sprint planning
End of engagementRTC EAC: your customer goes live under Early Adopter Care — triggers transition to Productization

Understand deployment dates early. Go-live may need to fall within the 90-day window, not just the end of development.

Starting an Execution engagement

Execution engagements are short-lived and greenfield — nothing is pre-established. The PM sets up the operating model from scratch. Plan for this in Week 1; do not assume any of it is already in place.

Week 1 setup

Before artifacts, stand up the working environment:

  • SharePoint document library — the shared workspace for both the delivery team and the client. Set up a folder structure from the start (e.g. Execution Documents, Sync & Discovery, Data Validation, Sprint Scope). The client cannot access your internal Jira board, so SharePoint is how they see your work.
  • Outlook distribution group — create a delivery team distro on the SAP side so meeting invites and team-wide communications go to one address rather than managing individuals
  • Client access — in some engagements the delivery team needs client email addresses (e.g. to be added to a client SharePoint). This takes time to arrange; start early. Do not assume Loop will work — SAP has restricted Loop functionality compared to ACN, and you may end up relying on a client SharePoint library instead
  • Communication channels — agree with the client how questions, decisions, and agenda items will be published and tracked before the first sync
